更新日: 2026-03-24

---

## 導入（感情・背景）
毎朝、ニュースサイトを巡回して、Xを見て、気になる投稿を保存して、
「で、今日は何からやるんだっけ？」って固まる。

この時点で、脳のHPが半分なくなる。
しかもサボってるわけじゃない。ちゃんと頑張ってるのに、前に進んでる感じがない。
この感覚が積み重なると、地味に自己嫌悪が溜まる。

だから週末に時間を作って、
**寝てる間にニュース収集→日本語要点化→朝の着手決定まで進む仕組み**を作った。

いまは朝、画面を一回開いて最初の1手を決めるだけ。
体感で30分、毎朝返ってきてる。

この文章では、
- なぜこの設計にしたか（考え方）
- どこで失敗したか（運用ログ）
- どうやって再現するか（実装手順）

を、順番に全部書く。

## 考え方（無料側で伝える核）

### 1) 朝は「判断」ではなく「着手」に使う
朝に必要なのは情報を増やすことじゃない。
**最初の1手を迷わず決めること**。

### 2) 収集・整理・実行を分ける
- 収集: 自動化
- 整理: 半自動
- 実行判断: 人間

この分離をしないと、全部が頭の中で混ざって重くなる。

### 3) 情報は取りすぎない
毎日3〜5件で十分。
多いほど賢くなるわけじゃなく、行動が遅くなるだけ。

### 4) 失敗前提で作る
自動化は壊れる。
だから「壊れた時にすぐ戻せる」を設計に入れる。

## 4. ニュース自動化ジョブ作成

### [VPS]
```bash
openclaw cron add \
  --name "daily-ai-news-lv1-0710" \
  --cron "10 7 * * *" \
  --tz "Asia/Tokyo" \
  --session isolated \
  --agent main \
  --message "過去24時間の主要AIニュースを3〜5件収集し、日本語で要点を短くまとめて報告。各項目に(1)何が起きたか(2)なぜ重要か(3)次アクションを含める。" \
  --announce \
  --channel discord \
  --to 1473005686257483826 \
  --json
```

> `--to` は自分の配信先に変更。

### 作成確認
```bash
openclaw cron list
```

## 5. 手動テスト（必須）

```bash
openclaw cron run <JOB_ID>
openclaw cron runs --id <JOB_ID> --limit 5
```

成功判定：
- status=ok

## 追加章1：実際の構築プロセス（時系列ログをそのまま公開）

ここからは、机上の理想論ではなく、実際に組んだ順番をそのまま書きます。
「何を」「どの順で」「どこで詰まったか」が分かれば、再現性は一気に上がります。

### フェーズA：動作確認できる最小形を先に作る
最初にやったのは、ニュース品質を高くすることではありません。
まずは「実行される」「届く」を確認する最小ジョブから始めました。

なぜか。
理由は単純で、ニュース内容の改善は、配信が安定してからで十分だからです。

最小形でやったこと：
- 1日1回の定時実行
- 送信先を1チャンネルに固定
- 日本語要点3〜5件のみ

ここでの狙いは、最短で成功体験を作ること。
「動いた」という事実があると、その後の改善が速くなります。

### フェーズB：手動実行テストで前倒し確認
定時を待たずに、手動実行で即テスト。

- ジョブ作成
- その場で run
- deliveryStatus 確認
- チャンネル到達確認

この手順を省くと、翌朝まで失敗に気づけません。
運用初期は、待ち時間を消すのが最優先です。

### フェーズC：配信は成功、でも中身が薄い問題
初回でありがちな失敗がこれ。

- 形式は届く
- でも実務に使える情報密度がない

対策は、出力フォーマットを先に固定すること。
「タイトル、何が起きたか、重要性、次アクション」の4点セットにしました。

結果、読む側が「結局どうすればいいの？」で止まりにくくなります。

### フェーズD：運用事故の再発防止
続けると、技術より運用事故が増えます。

代表例：
- タイミング競合
- 接続エラー
- 導線迷子

ここで効いたのは、
**エラー対応をその場の勘で終わらせず、再発防止ルールに落とす**ことでした。

## 追加章2：初心者がハマる「詰みポイント」10連発

### 1. 実行時刻の勘違い
症状：思った時刻に動かない。
原因：tz未設定、またはローカル時刻との混同。
対策：`--tz Asia/Tokyo` を必ず明示。

### 2. 送信先IDミス
症状：ジョブは成功扱いなのに見当たらない。
原因：`--to` が誤り。
対策：配信先IDをコピペ前に再確認。

### 3. announce忘れ
症状：内部実行のみで通知されない。
原因：`--announce` 未指定。
対策：配信目的ジョブは必ず announce 付き。

### 4. 手動テストを飛ばす
症状：翌朝まで失敗に気づかない。
対策：作成直後に `cron run` を必須化。

### 5. 内容改善を先にやりすぎる
症状：品質だけ上げて配信安定しない。
対策：「届く→整える」の順序厳守。

### 6. ログを見ない
症状：同じ失敗を繰り返す。
対策：`cron runs` を毎日1回見る習慣。

### 7. いきなり複数ジョブ
症状：どこが壊れてるか分からない。
対策：最初はニュース1本だけ。

### 8. 接続手段が1本しかない
症状：DNSこけたら終わる。
対策：ホスト名とIP直の二重導線。

### 9. 新規ページに導線がない
症状：作っただけで使わない。
対策：新規作成=フォルダー追加までを完了条件。

### 10. 完璧主義
症状：公開前に疲れて止まる。
対策：まず70点で回し、週次改善。

## 追加章4：環境差分があっても再現しやすくする工夫

「同じコードがそのまま動かない」問題は、ほぼ必ず起きます。
なので、最初から差分管理の発想で書きます。

### 差分管理の3点
1. 固定値を最小化
2. 変数化できる箇所を明記
3. 代替手順をセットで書く

例：
- 配信先IDは差分
- 実行時刻は差分
- タイムゾーンは差分
- でも実行フローは共通

この「共通と差分の分離」ができると、再現性が跳ね上がります。

## 追加章9：実行コマンドを読むのが苦手な人向け解説

ここは「コマンドは怖い」という人向けです。

### `openclaw cron add` は何をしている？
新しい自動実行予約を作る命令です。

### `--name` は何をしている？
予約の名前を付けています。後で探すために使います。

### `--cron "10 7 * * *"` は？
毎日7:10に実行する設定です。

### `--tz "Asia/Tokyo"` は？
日本時間で解釈させる指定です。

### `--message` は？
実行時にAIへ渡す具体的な指示文です。

### `--announce --channel --to` は？
結果をどこへ送るかを指定しています。

この理解があると、コピペの怖さが減ります。
