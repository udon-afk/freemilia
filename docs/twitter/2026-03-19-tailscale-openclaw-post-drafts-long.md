# X Post Drafts (Longform) — TailscaleでOpenClaw VPS×実機接続成功

## Long Draft A（拡張性メイン・本命）
OpenClaw、Tailscale経由で **VPS×実機接続** まで通せた。  
ここが今回の一番でかい進捗。

何が良いかというと、
「とりあえず1台で全部やる」構成から抜けて、
**役割分離したまま後から機能を足せる** 状態に入れたこと。

具体的には、
- VPS側は常時稼働・監視・通知などの制御寄りを担当
- 実機側は重い処理（描画/変換/将来的な拡張処理）を担当
- 接続はTailscaleで閉域化して、無理な外部公開を避ける

この構成にすると、
「どこか1点が詰まったら全部止まる」から、
「詰まった部分だけ差し替える」運用に寄せられる。

つまり、単発で動かして終わりじゃなくて、
**運用しながら育てられる基盤** ができたのが今回の価値。

次はこの土台の上で、
- 実機オフロードの基準を明文化
- 障害時の切り戻し手順を固定
- 追加機能を段階投入
の順で伸ばしていく。

“接続できた” というより、
**拡張できる設計に乗せられた** のが収穫。

## Long Draft B（技術運用寄り）
TailscaleでOpenClawのVPS↔実機疎通に成功。  
見た目は地味だけど、運用としてはかなり大きい。

これまでの課題は、
- 1ノード集中で負荷も責務も偏る
- 何か崩れると全体が止まりやすい
- 拡張するたびに既存構成を壊しがち

今回の接続で、
**制御レイヤー（VPS）と実行レイヤー（実機）を分離** できるようになった。

この分離のメリットは3つ。
1. 変更の影響範囲を局所化できる
2. 重処理を実機へ逃がして全体安定性を上げやすい
3. 将来機能を“横に足す”拡張がしやすい

要するに、
フル機能を最初から詰め込む設計ではなく、
**小さく繋いで、止めずに育てる設計** に移行できた。

次フェーズは、
- どの処理をどちらで実行するかのルール化
- メトリクス取得と閾値の定義
- 障害時フォールバックの自動化

この順で、運用の再現性を上げていく予定。
